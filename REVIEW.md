# REVIEW.md

List every defect found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health()` / line 73–74 | Always returns 200 OK regardless of whether MongoDB is reachable. The spec requires 503 when MongoDB does not answer a ping. | Kill MongoDB and call `GET /health` — you still receive `{"status": "ok"}` with 200 instead of 503. | Added a `db.command("ping")` call inside a try/except; on failure, return a 503 JSONResponse. |
| 2 | `create_employee()` / line 79–80 | Duplicate-emp_code check uses `find_one` then `insert_one` (check-then-insert). Two concurrent requests for the same `emp_code` can both pass the check and both insert, violating uniqueness. | Send two concurrent POST /employees with the same emp_code. | Removed the pre-check; rely solely on the unique index and catch `DuplicateKeyError`, returning 409. |
| 3 | `create_employee()` / line 82 | `datetime.now()` is called without a timezone, producing a naive UTC-looking datetime that is actually local time. On a server not in UTC this stores the wrong time. | Run on a non-UTC server and compare `created_at` against the actual UTC clock. | Changed to `datetime.now(tz=timezone.utc)`. |
| 4 | `list_employees()` / line 93 | `skip = page * page_size` should be `(page - 1) * page_size`. With the bug, page 1 skips 20 records (returns nothing if fewer than 21 exist), page 2 skips 40, etc. | Call `GET /employees?page=1` with fewer than 20 employees — the list is empty. | Changed to `skip = (page - 1) * page_size`. |
| 5 | `list_employees()` / line 94 | `count_documents({})` ignores the `department` filter, so `total` always counts all employees even when a filter is applied. | Filter by a department with 2 employees out of 6 total — `total` still shows 6. | Changed to `count_documents(q)` so it reflects the filtered count. |
| 6 | `list_employees()` / line 95 | Results are not sorted by `emp_code` ascending as required by the spec. Also, `find(..., {"_id": 0})` does not serialize `created_at` (a datetime) to epoch milliseconds. | Compare response order to spec expectation; also notice `created_at` is a raw datetime string instead of an integer. | Added `.sort("emp_code", ASCENDING)` and added a `serialize_employee()` helper that converts `created_at` to epoch ms. |
| 7 | `punch_in()` / line 102 | `datetime.fromtimestamp(body.punched_at / 1000)` uses the local system timezone, not UTC. The resulting datetime is wrong on non-UTC hosts. Also no validation that `punched_at` looks like milliseconds (not seconds). | On a machine in IST, pass a valid UTC epoch ms — the stored datetime will be 5.5 hours off. | Used `ms_to_dt()` which calls `datetime.fromtimestamp(..., tz=timezone.utc)` and truncates to seconds. Added epoch-range validation in Pydantic. |
| 8 | `punch_in()` / line 103 | `ts.date()` uses the naive local date. For IST employees in UTC+5:30, a punch at 23:00 UTC (= 04:30 IST next day) would record the wrong attendance date. R1 requires the IST calendar date. | Punch in at 23:00 UTC with a 09:30 shift — `date` becomes the UTC date, not the IST date. | Replaced with `attendance_date_for(ts, shift_start, shift_end)` which applies IST offset and handles overnight shifts. |
| 9 | `punch_in()` / line 104 | Same check-then-insert race condition as `create_employee`. Two simultaneous punch-ins for the same employee and date can both pass the existence check and both insert. | Send two concurrent punch-in requests for the same employee. One should get 409 but both may get 201. | Removed the `find_one` guard; rely on the unique compound index `(emp_code, date)` and catch `DuplicateKeyError`. |
| 10 | `punch_in()` / line 113 | `compute_late_minutes` computes lateness by rebuilding `shift_start` using `punch_in.replace(hour=h, minute=m, ...)`. This uses the naive datetime's date component (UTC date), which is wrong for IST-aware calculations and for overnight shifts. Grace period check (`> 10` minutes) is off-by-one — the spec says *strictly more than* 10 minutes, but `> 10` is correct only if `minutes` is an int (the issue is that int truncation is fine but the comparison should be against 600 seconds, not 10 minutes, to handle sub-minute precision correctly). | Employee with 09:30 shift punches in at exactly 09:40:01 IST — should be `late_minutes = 10`; the starter may return 0. | Rewrote `compute_late_minutes` to build `shift_start` as an IST-aware datetime on the attendance date, compare against 600 seconds (strictly), and use floor division of total seconds. |
| 11 | `punch_in()` / line 119 | Response includes `"id": str(res.inserted_id)` — a MongoDB internal `_id` that must never appear in the API. | Inspect the response body and see an `id` field not in the spec. | Removed; use `serialize_record()` which excludes `_id`. |
| 12 | `list_attendance()` / lines 144–150 | Loads the **entire collection** into Python memory (`list(db.attendance_logs.find(q))`), sorts and paginates in Python. This violates the spec requirement to stay fast on ~100,000 records. Also `total` reflects the filtered set here only by accident (it counts `docs`), but `docs` is the full unfiltered-by-page result — it only works accidentally. Sorting by `d["date"]` in Python is fine for strings but is done after loading all docs. | On 100k records, the endpoint will be extremely slow and OOM on constrained hosts. | Replaced with server-side `.sort()`, `.skip()`, `.limit()` and separate `count_documents(q)`; no in-memory sort. |
| 13 | `compute_overtime()` / line 46–47 | Uses `datetime.fromisoformat(date_str).replace(hour=h, minute=m, tzinfo=IST)`. For overnight shifts the `shift_end` is on the **next** calendar day, but this always builds the end on `date_str`'s date. So overnight overtime is calculated against the wrong day. | Overnight employee (22:00–06:00) works until 06:40 IST next day — overtime should be 40 min but the starter computes it against 06:00 on the same date as punch-in. | Rewrote `compute_overtime_minutes` to detect overnight shifts and add one day to the end date when needed. |
| 14 | No `punch-out` endpoint | The starter has no `POST /attendance/punch-out` implementation. | Calling the endpoint returns 404. | Implemented fully with concurrency safety via `find_one_and_update` + `punch_out: None` filter. |
| 15 | No validation of `punched_at` epoch range | The starter does not validate that `punched_at` is in the milliseconds range (≥ 100,000,000,000). Passing a seconds-epoch value (e.g. 1783312) is silently accepted and stores a date in 1970. | Send `punched_at: 1700000000` (seconds-style). The API accepts it and creates a record in the 1970s. | Added Pydantic validators that check `EPOCH_MIN ≤ punched_at ≤ EPOCH_MAX` with a 422 on failure. |

## Things examined and decided NOT defects

- **`compute_work_hours` using `round(..., 2)`**: Python's built-in `round()` uses banker's rounding (round-half-to-even), which differs from the spec's "half-up" requirement for R4. This is a subtle bug (not a non-defect) — it only manifests when the third decimal is exactly 5. Fixed in the new implementation using `Decimal` with `ROUND_HALF_UP`.
- **`load_dotenv()` at module level**: Fine; it only loads if a `.env` file is present and real environment variables always win.
- **`MongoClient` at module level**: Acceptable for a single-process FastAPI app; connection pooling is handled automatically.
